The baseline was the day's first Flint boot, and every later arm reads +3–5 % at every depth, so that band is the boot
effect, not the flag (bf16sum and swa010 produce byte-identical outputs and sit inside it). FP8 KV adds a further +3 %
at 117K and **doubles both pools** at equal quality on these cells. NGRAM is content-bound: the repetitive `decode_ab`
prompt lets it accept 4–8 drafts at 14 / 7.3K (105 / 79 tok/s medians), but at 58K / 117K it is *below* no-spec
(35 / 26 vs 39.6 / 36.3) because Flint's sinks keep the verify step on the stock tree kernel (patch 107/110's split-KV
route serves plain extends, not NGRAM's tree), and on non-repetitive text the accept length is 1.5–1.7.

**Copy-heavy decode** (`copyheavy_decode_bench.py`, reproduce one source file verbatim after a 27K / 57K prompt, 600
tokens; server-log gen throughput, median of the decode batches): baseline 41.1 / 40.0 tok/s, fp8kv 42.1 / 41.5, bf16sum
42.8 / 41.2, swa010 42.5 / 41.0, **NGRAM 26.4 / 24.9 with accept length 1.4 / 2.0** — even on its own best case Flint's
NGRAM arm loses 35–40 % to the per-step verify, so NGRAM is off for Flint (unchanged).

## Disposition

- **NGRAM speculation: off** (loses 35–40 % even on copy-heavy decode; the verify stays on the stock tree kernel).
- **SWA ratio: stays 0.02** — a pool-split trade with no speed effect (0.10 gives the SWA layers 44K tokens and takes the
  full-attention pool from 525K to 441K).
- **BF16 attention sum: null**, reverted (byte-identical outputs, ±2 %).
- **FP8 KV: recommended, user decision** — +2–8 % decode (most at depth), **2× pools** (1,050,610 full / 21,012 SWA tokens),
  needle 11/12 vs 10/12 with one cell swap at the 243K soft edge. It is a KV-dtype change on a model whose 243K retrieval
  edge is soft under either dtype, so it waits for the user like the qwen35 holds; `KV_DTYPE=fp8_e4m3` runs it today.
